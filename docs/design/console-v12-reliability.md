# 第一阶段：管理协议与任务反馈修复

本轮在真实管理 API 版本上推进已确认的第一阶段。沿用 Node 服务、原生 JS 工作台和单实例 JSON 存储，重点修复执行回执、重试边界、配置并发、容量降级与任务详情反馈。

## 已交付的行为

| 模块        | 改动                                                                     | 对使用者的影响                                                    |
| ----------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Worker 接口 | 领取、心跳、提案、完成和取消确认只返回本次协议所需数据                   | Worker 不会从响应中获得管理快照                                   |
| 成功回执    | 按审批动作校验 commit、PR、Issue 和文件清单                              | 不相符的成功结果不能被当成已授权执行                              |
| 中断回执    | 持久保存部分、取消及迟到回执，并支持相同回执幂等重放                     | 中断后仍能查到外部变更证据；任务不会被迟到回执改为成功            |
| 人工核对    | 管理员记录核对结论和说明，保留历史                                       | 结果不明确时先核对，再决定是否重试                                |
| 重试链      | 检查原任务及全部重试祖先；新证据到达时停止未运行后继、请求取消运行中后继 | 已排队或审批的重试不会绕过原任务的核对要求                        |
| 配置版本    | 规则和监控配置分别使用独立版本                                           | Worker 心跳不会让未修改过的配置草稿失效；真正的并发修改仍返回冲突 |
| 存储降级    | 容量或写入失败时继续提供最后成功保存的快照，并关闭写能力                 | 页面仍可查看、导出，明确显示只读原因；不删除历史换取空间          |
| 任务详情    | 展示最终动作、产物、安全外链、失败原因、回执与核对记录                   | 在同一详情中了解结果和下一步，不增加侧栏模块                      |
| 详情更新    | 只读详情继续轮询，保留标签、滚动、焦点和回执展开状态                     | 页面能跟进执行进度，同时保护正在编辑的核对说明                    |
| 质量检查    | 恢复 ESLint 9 对真实 JS/MJS 源码、脚本和测试的检查                       | lint 成为有效检查项；框架 TypeScript 检查继续保留                 |

## 回执与核对的具体边界

成功的 `committed` 只允许 commit；`pr-created` 允许 PR 及其 commit；`issue-created` 只允许 Issue；`retry` 和 `skipped` 不允许外部产物。代码产物的文件清单必须与已批准候选一致。失败或中断时报告的副作用会作为证据保留，不能借此扩展成功动作的授权。

相同租约、身份和内容的完成/取消回执可以在重启后重放。普通终态任务不能通过改写完成回执覆盖结果。只有服务记录的真实中断允许补录新的迟到证据；Worker 自报的错误名称不会授予该能力。私有租约、回执指纹和中断标记不进入管理快照。

执行取消、失联或失败后，管理者通过 `POST /api/healing/tasks/:id/reconcile` 记录核对结果。说明必填；已经有变更证据时不能选择“确认未发生变更”。接口要求管理身份、任务版本和浏览器 CSRF，并支持请求幂等。该功能记录人工核查结论，尚不代表服务已自行向 GitHub 或 CI 验证结果。

新的执行证据可以使旧结论重新变为待核对，并沿重试链阻止后继执行。停止原因通过 `execution.blockedByReconciliation` 展示，详情可以打开原任务。重新核对原任务后，已停止的任务不会自动恢复；管理者可以根据当前状态另行重试。运行中的后继只能被请求取消，不能宣称远程进程已经停止。

等待审批的后继被停止时，同时结束其活动审批状态；已完成的关卡决定、检查结果、证据和审批历史继续保留。详情与审批列表统一显示终态，核对完成后可显式重试。启动迁移也修复已保存的“任务已取消、审批仍待处理”状态。“重试任务已停止”以中文呈现，并归入任务操作筛选。

没有新结果的迟到取消确认不会推翻已保存的结论。重复回执不会重复产生审计或核对历史。单任务最多保留 10 份不同回执、100 条核对历史，超限明确拒绝新增，不能静默截断。

## 旧数据与配置兼容

旧状态文档保持 `schemaVersion: 1`。迁移根据已有产物和中断事实补充必要的待核对状态，不伪造旧租约，不删除任务、结果或审批记录。已知仅发生在诊断阶段的超时不应被当成未知执行结果。

新快照提供 `configRevisions.rules` 和 `configRevisions.monitoring`。新版 UI 保存配置时传 `expectedConfigRevision`；旧客户端仍可使用全局 `expectedRevision`。如果旧客户端只使用全局版本，它仍可能在 Worker 更新后遇到原有的版本冲突。

Worker 成功响应不再包含管理 `snapshot`。任何依赖该旧字段的适配器应改为消费本任务确认字段；管理页面继续通过管理身份读取快照。详细结构见 [Agent 接入协议](../agent-worker-api.md) 和 [管理 API](../console-api.md)。

## 容量降级与恢复

达到容量上限或持久化失败时，快照返回 `storage.status: "read-only"`、原因、说明和各项用量，所有写能力为 false。管理页面仍显示最后成功保存的数据。若租约过期事务无法落盘，界面可能暂时保留最后保存的运行状态，存储警示会说明未保存的状态变化；不会把内存中尚未提交的失败结果显示为已保存事实。

单份审批历史达到 10,000 条时，安全停止仍保留全部历史和审批决定，使用任务取消状态及原任务停止标记记录原因，不假装追加了新历史；实时补录仍保存回执和停止审计。此处理不放宽全局容量限制，也不改变普通审批/取消的容量检查。

本轮没有增加自动归档或清理。恢复容量前应先备份，再通过受控维护或后续数据库迁移处理；不要在线修改状态文件。暂时性写入错误在下一次成功持久化或服务重启后重新评估。完整行为和限制见 [配置版本与存储恢复](../console-storage-recovery.md)。
